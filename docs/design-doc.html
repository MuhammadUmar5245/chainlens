Design document · v0.2

Chainlens: on-chain behaviour analytics for Bitcoin, Ethereum, EthereumPoW, Ethereum Classic and Solana

A web platform that pulls blockchain transactions from an API, a database or an uploaded data dump, runs wallet-behaviour analytics over millions of records, stores the results in a database, and shows them in a React dashboard filtered by chain.

Status decisions confirmed; first working version built (see Roadmap) Updated 7 Oct 2026 Name "Chainlens" is a working title

01Overview

The platform answers one question for any supported chain and time range: how are wallets behaving, and which ones stand out? It does this in four steps that run as one tracked job:

  1. Get data from one of three sources: the NOWNodes blockchain API, an existing database, or a file the user uploads (a "data dump").
  2. Store the raw transactions in an analytics database, one normalised format for every chain.
  3. Analyse: build wallet features, assign behaviour tags, score anomalies and group wallets into clusters.
  4. Save and show: write the results back to the database and serve them to a React dashboard, where everything can be filtered by chain.

In scope for version 1

  • Five chains, selectable with a chain filter across the whole app.
  • Fetch from API, import from a database, and upload a data dump (CSV, Parquet, JSON Lines, Excel).
  • Analytics that keep working at tens of millions of transactions.
  • Database setup and configuration for the backend, runnable locally with one command.
  • React dashboard: overview, per-block charts, tags, clusters, wallet explorer, wallet detail, job progress.

Not in version 1

  • Token transfers (ERC-20 logs), internal transactions and USD pricing. v1 analyses native-coin transactions only, like the current script.
  • Real-time streaming. v1 works in jobs over block ranges.
  • Multiple user accounts and roles. v1 assumes one trusted team; login comes in a later phase.

How Bitcoin and Solana fit the same table

  • Bitcoin has inputs and outputs, not from/to. The sender is the address of the largest input; each output to another address becomes one row (tx_hash = txid:output). Change back to the sender is left out; newly mined coins have sender coinbase. One Bitcoin transaction can therefore be several rows; counts for Bitcoin are payments, not transactions.
  • Solana has no value field. The sender is the fee payer, the receiver is the account whose SOL balance rose most (or the program called when no SOL moved), and the value is that rise. Vote transactions, about half of all Solana transactions, are skipped.
  • Addresses: hex addresses are lowercased; Bitcoin and Solana addresses are case-sensitive and kept exactly.

What 30 days of history costs

One API call per block (or slot). Bitcoin and Solana blocks are large, so each call takes much longer; these times were measured on NOWNodes and drive the estimate on the Data screen.

Solana needs a different approach

Solana makes about 2.5 slots per second and each slot takes about 35 seconds to download, so the API cannot keep up or backfill 30 days. Solana is supported for recent samples (a few hundred slots) and for data dumps. Full Solana history needs a bulk data source; this is listed under Risks.

Volume estimates for 30 days: Ethereum about 60 million transactions; Bitcoin about 30 million payment rows; EthereumPoW and Ethereum Classic far fewer (in the samples, a handful of transactions per block).

Per-chain settings

Each chain has its own row in the chains table: family, endpoint, coin symbol and decimals, fee unit, whale threshold in its own coin, request rate limit, parallel workers, typical time per call, and an explorer link template. Another EVM chain is a new row; a new family (for example Tron) needs a new adapter.

Why two databases

The analytics workload is "group 50 million rows by wallet and sum them". A column store like ClickHouse does this in seconds; a row store like PostgreSQL slows down past tens of millions of rows. The app's own records (jobs, settings) are small, change often and need transactions, which PostgreSQL does best. Each database does the work it is built for.

Why Python for the backend

The existing analytics, the Claude agent and the clustering code are all Python. Keeping the backend in Python reuses that code. The React frontend is independent of this choice.

Side benefit

On the current Windows machine, an Application Control policy blocks scikit-learn's SciPy files, which is why the script falls back to its own KMeans. The backend runs in Linux Docker containers, so scikit-learn works normally there.

Job lifecycle

Each job moves through queued → running → succeeded | failed | cancelled. Workers report progress (for example "4,210 of 7,200 blocks") to PostgreSQL, and the React app polls it every 1.5–2 seconds while a job is active.

Source 1: fetch from API

  • Input: chain, and either "last N blocks" or a block range or a time range (converted to blocks).
  • The block range is split into chunks of 1,000 blocks. Chunks run in parallel within the chain's rate limit.
  • Each chunk writes its rows in batches of about 10,000 and records a checkpoint. A retried or resumed job continues from the last checkpoint.
  • Errors such as HTTP 429 back off and retry, as the script already does. Blocks that still fail are listed in the job result, not silently skipped.

Source 2: data dump upload

  • Supported: CSV, Parquet, JSON Lines, Excel (.xlsx). v1 streams the upload to disk; resumable uploads (tus protocol) and S3-style storage follow in phase 5.
  • The app previews the first rows, suggests a mapping from common column names, and lets the user correct it. Required: tx_hash, timestamp, from, to, value, plus a chain (one for the whole file, or a chain column). Optional: block number, gas price, gas limit, contract-call flag or input data, nonce. Value can be in whole coins or wei; gas in gwei or wei.
  • The file is read in chunks of 100,000 rows, so memory stays flat for files with millions of rows.
  • Rows that fail validation go to a rejects file the user can download. The job reports how many were loaded and how many rejected.
Excel limit

An Excel sheet holds at most 1,048,576 rows. For dumps of millions of records, CSV or Parquet is required; the upload screen says so.

Source 3: import from a database

  • User saves a connection (PostgreSQL or MySQL) and writes a read-only SELECT.
  • The worker streams the result in chunks of 50,000 rows using a server-side cursor, then maps columns the same way as an upload.
  • Saved connections can be re-run to pull new rows since the last import.

Duplicates

The same transaction can arrive twice (an overlapping fetch, a re-uploaded file). The transactions table keys on (chain, block_number, tx_hash) and keeps one copy, so re-running any job is safe. Fetch jobs also checkpoint every 1,000 blocks, so a retried job continues where it stopped.

07Data model

ClickHouse: data and results

CREATE TABLE transactions (
  chain             LowCardinality(String),
  dataset_id        UInt64,
  block_number      UInt64,
  block_time        DateTime,
  tx_hash           String,
  from_addr         String,
  to_addr           String,          -- 'contract_creation' when empty, as today
  value_native      Float64,         -- value / 10^decimals of the chain's coin
  gas_limit         UInt64,
  gas_price_gwei    Float64,
  is_contract_call  UInt8,
  nonce             UInt64,
  source            LowCardinality(String),   -- 'api' | 'upload'
  ingested_at       DateTime DEFAULT now(),
  INDEX idx_from from_addr TYPE bloom_filter GRANULARITY 4,
  INDEX idx_to   to_addr   TYPE bloom_filter GRANULARITY 4
)
ENGINE = ReplacingMergeTree(ingested_at)
PARTITION BY (chain, toYYYYMM(block_time))
ORDER BY (chain, block_number, tx_hash)
TTL block_time + INTERVAL 30 DAY DELETE WHERE source = 'api';

The TTL removes fetched data after 30 days. Uploaded dumps are kept until their dataset is deleted, so historical files are never removed by surprise. The bloom-filter indexes make wallet look-ups fast without scanning the whole chain.

08Analytics engine

The rules are the same as the current script. What changes is where they run: in ClickHouse, next to the data, so nothing has to be loaded into memory row by row.

StepRule (from the script)How it runs at scale
Wallet featuresGroup by sender and by receiver; join; fill missing with 0One SQL query: sent and received aggregates combined with UNION ALL, grouped by wallet
Whalevolume ≥ threshold (100 ETH today)Simple filter; threshold read from the chain's settings
High-frequency bottx_out ≥ max(95th percentile, 5) and ≥ 1.5 tx per active blockPercentile from quantile(0.95), computed per chain
Hub / exchange-likesenders or receivers ≥ max(99th percentile, 10)Same, with quantile(0.99)
Contract-heavytx_out ≥ 3 and ≥ 90% contract callsSimple filter
One-offexactly one transaction in totalSimple filter
Anomaly scoreRMS of z-scores of 7 log-scaled features; anomaly at ≥ 3.0Two passes: means and standard deviations per chain, then the score per wallet
ClustersKMeans, k = 4, on 9 standardised log featuresPython worker: fit MiniBatchKMeans on a sample of up to 1 million wallets, then assign every wallet in batches
Important for multi-chain

Percentiles, z-scores and clusters are calculated per chain. Mixing chains would let the busiest chain decide what "unusual" means for all of them. When the dashboard shows several chains together, each wallet still carries its own chain's scores.

The settings used for a run (thresholds, k, sample size) are saved with the run, so any result can be explained and reproduced later.

The chain filter

A filter bar sits at the top of every screen: chain (multi-select of the five), dataset (or "all data"), time range and tag. Changing it updates the URL and every panel on the screen. Each chain keeps a fixed colour everywhere in the app, so Ethereum is always the same colour whichever chains are selected.

12Security

  • API keys stay on the server. The React app never calls NOWNodes or Anthropic itself; any key shipped to a browser can be read by anyone who opens the page.
  • No keys in code. The current script has the NOWNodes key typed into the file. In the platform, keys live only in .env or a secrets manager, and .env is in .gitignore. The existing key should be rotated before the code goes into a shared repository.
  • Saved database passwords are encrypted with SECRET_ENCRYPTION_KEY and never returned by the API.
  • External imports are read-only. Only a single SELECT is accepted, and the connection is opened read-only.
  • Any user-written SQL (if offered later) runs as the ClickHouse read-only user with row and time limits.
  • Uploads are checked for type and size, stored outside the web root, and never executed.
  • Login: v1 is meant for a trusted team behind a private network or VPN. Accounts and roles are planned for phase 6, before any public deployment.
